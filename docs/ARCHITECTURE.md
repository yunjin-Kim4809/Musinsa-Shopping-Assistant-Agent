## 1. 계층 구조

```
interfaces (api/, cli.py)        ← HTTP/터미널 어댑터. 얇게 유지
        │
services (services/)             ← 비즈니스 로직. SearchClient "프로토콜"에만 의존
        │
analysis (analysis/)             ← 순수 알고리즘. I/O 없음
infra    (infra/)                ← 외부 세계와의 경계. 안정화 부품
        │
domain   (domain/)               ← 순수 데이터 모델. 어디에도 의존하지 않음
```

**의존 방향은 항상 아래로만** 흐릅니다. 핵심 규칙:

- **서비스는 Tavily의 존재를 모른다.** `SearchClient` 프로토콜(구조적 타이핑)에만
  의존하므로, 테스트에서 가짜 클라이언트를 주입해 전체 로직을 네트워크 없이 검증한다
  (의존성 역전 원칙). 139개 테스트 전부가 API 키 없이 돈다.
- **분석 계층은 순수 함수/자료구조**다. Aho-Corasick, BM25, 편집 거리 모두
  입력→출력만 있는 결정적 코드라서 단위 테스트가 쉽고 재사용이 자유롭다.
- **조립은 한 곳에서** (`api/deps.py` 의 `build_container`). 설정 → 인프라 부품 →
  클라이언트 → 서비스 순으로 객체 그래프를 만드는 composition root 패턴.

## 2. 외부 API 호출 안정화 파이프라인

검색 1회는 다음 4겹을 통과합니다:

```
search(query)
  └─ ① TTL-LRU 캐시 ── 적중 시 즉시 반환 (호출·과금 없음)
  └─ ② singleflight ── 동일 키 동시 미스를 원격 호출 1회로 병합
       └─ ③ 재시도 루프 (지수 백오프 + full jitter, 최대 3회)
            └─ ④ 토큰 버킷 ── 초당 호출량 제한 (대기)
            └─ ⑤ 서킷 브레이커 ── 연속 실패 시 즉시 차단
                 └─ ⑥ Tavily 원격 호출
```

**조합 순서가 곧 설계**입니다:

| 결정 | 근거 |
|------|------|
| 캐시가 가장 바깥 | 적중하면 rate limit 토큰도 아낀다 |
| singleflight 가 캐시 바로 안쪽 | 캐시는 시간축 중복(끝난 호출), singleflight 는 동시성축 중복(진행 중 호출)을 제거 — 조합하면 cache stampede 가 사라진다 |
| 서킷 브레이커가 원격 호출 바로 앞 | 실패 카운트가 "실제 원격 실패"만 반영. rate limit 대기 초과 같은 클라이언트 사정은 실패로 세지 않음 |
| `CircuitOpenError` 는 재시도 제외 | "서버가 죽었다"는 판정을 받고도 백오프 재시도하는 것은 무의미. 즉시 `SearchUnavailableError` 로 승격 → API 계층이 **503 + Retry-After** 로 응답 |
| 병렬 fan-out 은 부분 성공 허용 | 쿼리 8개 중 3개 실패해도 5개 결과로 진행. 전부 실패 + 서킷 차단이면 그때만 503 |

이 체인은 실제로 동작합니다. 잘못된 API 키로 서버를 띄우면:
연속 인증 실패 → 5회째에 서킷 OPEN → 이후 요청은 원격 호출 없이 즉시
`503 {"error": "search_backend_unavailable"}` + `Retry-After` 헤더.

## 3. CS 기술 상세

### 3.1 TTL-LRU 캐시 — `infra/cache.py`

**왜**: 같은 검색어의 반복 호출(비교→재비교, 여러 사용자의 인기 검색어)마다
수백 ms 지연 + 과금이 발생한다.

**어떻게**: 해시맵(key→노드) + **이중 연결 리스트**(사용 순서) 조합.

- `get`: 해시맵 조회 O(1) → 노드를 리스트 head(MRU)로 이동 O(1)
- `put`: 용량 초과 시 tail(LRU) 노드 제거 O(1)
- TTL 은 **lazy expiration**: 타이머 스레드 없이 get 시점에 만료 검사
- 센티널 노드 2개로 빈 리스트/경계 분기 제거
- `RLock` 으로 스레드 안전 (FastAPI 스레드풀 + 병렬 검색에서 동시 접근)

**트레이드오프**: `get_or_set` 의 factory 는 락 밖에서 실행한다. 외부 API 호출(수백 ms)이
락을 쥐면 모든 캐시 접근이 직렬화되기 때문. 대신 같은 키의 동시 미스(cache stampede)는
허용한다 — 트래픽 규모상 중복 호출 1~2회가 락 경합보다 싸다.

**면접 포인트**: "OrderedDict/functools.lru_cache 로도 되는데 왜 직접 구현했나?" →
TTL·통계·스레드 안전을 한 자료구조에서 다루려면 내부 제어가 필요하고,
O(1) 보장의 원리(해시맵이 위치를, 연결 리스트가 순서를 담당)를 이해하고 있음을 보여줄 수 있다.

### 3.1.1 Singleflight — `infra/singleflight.py`

**왜**: 캐시는 "이미 끝난 호출"만 재사용한다. 인기 검색어의 캐시가 만료되는 순간
동시 요청 N개가 전부 미스가 되어 N번의 원격 호출이 나간다 (**cache stampede**).

**어떻게**: Go 의 `golang.org/x/sync/singleflight` 패턴. 같은 키의 동시 호출 중
첫 스레드(리더)만 실제 실행하고, 나머지(팔로워)는 `threading.Event` 로 리더의
완료를 기다려 결과를 공유받는다.

- 리더 선출은 락 안의 dict 등록으로 원자적으로 결정
- **리더의 예외도 팔로워 전원에게 전파** — 성공만 공유하면 실패 순간
  팔로워들이 일제히 재호출해 stampede 가 재발한다
- flight 완료 즉시 테이블에서 제거. 결과 "보존"은 캐시의 몫, singleflight 는
  "합류"만 담당 (역할 분리)
- 리더 완료 직후 합류 실패한 스레드를 위해 flight 내부에서 캐시를
  재확인(double-check)한다

통합 테스트: 동일 쿼리 동시 요청 8개 → 원격 호출 정확히 1회 검증.

**면접 포인트**: 캐시 TTL 지터, 조기 갱신(early recomputation), 락 기반
per-key mutex 와의 비교. 분산 환경이라면 Redis 분산 락 또는 요청 코얼레싱 프록시.

### 3.2 토큰 버킷 — `infra/rate_limiter.py`

**왜**: 검색 API 쿼터/과금 한도를 클라이언트가 선제적으로 지켜야 한다.
고정 윈도우 카운터는 윈도우 경계에서 2배 폭주(boundary burst)가 가능하다.

**어떻게**: 버킷에 초당 `rate` 개 토큰이 차고, 요청은 토큰을 소비한다.

- **lazy refill**: 백그라운드 스레드 없이 접근 시점에 `경과 시간 × rate` 만큼 일괄 충전
- `time.monotonic` 사용 — 시스템 시간 변경(NTP 보정)에 영향받지 않음
- 대기 시 부족분이 채워질 시각을 계산해 **정확히 그만큼만 sleep** (busy-wait 없음)

**두 곳에서 재사용**: ① 외부 검색 API 호출 제한(블로킹 `acquire`),
② API 미들웨어의 클라이언트(IP)별 rate limit(논블로킹 `try_acquire` → 429).
클라이언트별 버킷 저장소로는 직접 만든 TTL-LRU 캐시를 재사용해 유휴 클라이언트의
버킷이 자동 정리된다 (무한 dict 증가 방지 — 메모리 유계).

**면접 포인트**: leaky bucket 과의 차이(토큰 버킷은 버스트 허용), 분산 환경이라면?
(Redis + Lua 스크립트로 원자적 구현).

### 3.3 서킷 브레이커 — `infra/circuit_breaker.py`

**왜**: 외부 API 장애 시 실패할 게 뻔한 호출을 타임아웃까지 기다리며 반복하면
스레드/시간이 장애에 잠식된다(cascading failure).

**어떻게**: 3-상태 머신.

```
CLOSED --(연속 실패 ≥ threshold)--> OPEN --(recovery_timeout 경과)--> HALF_OPEN
   ▲                                                                    │
   └────────────── 프로브 성공 ──────────────────────────────────────────┘
                   프로브 실패 → 다시 OPEN
```

- HALF_OPEN 에서 **동시 프로브 수를 제한** — 복구 순간 모든 스레드가 한꺼번에
  프로브를 쏘면 회복 중인 서버를 다시 쓰러뜨릴 수 있다
- 상태 전이는 락으로 원자적으로 수행, `snapshot()` 으로 관측 노출 (`/api/v1/stats`)

**면접 포인트**: 왜 실패 "비율"이 아닌 "연속 횟수"인가? → 트래픽이 적은 서비스에서
비율 기반은 표본이 작아 오판이 잦다. Netflix Hystrix 는 슬라이딩 윈도우 비율,
resilience4j 는 둘 다 지원 — 트래픽 특성에 따른 선택.

### 3.4 지수 백오프 + Full Jitter — `infra/retry.py`

**왜**: 일시적 네트워크 오류는 재시도로 복구되지만, 고정 간격 재시도는 실패 시점이
같았던 클라이언트들이 **동시에** 재시도하는 thundering herd 를 만든다.

**어떻게**: `대기 = U(0, min(max_delay, base × 2^attempt))` — AWS Architecture Blog 의
"Exponential Backoff and Jitter" 에서 권장하는 full jitter. 지수적으로 커지는 상한 안에서
균등 난수로 재시도 시점을 분산시킨다.

**면접 포인트**: equal jitter/decorrelated jitter 와의 비교. full jitter 가 서버 부하
분산에 가장 효과적이라는 AWS 시뮬레이션 결과.

### 3.5 Aho-Corasick 다중 패턴 매칭 — `analysis/aho_corasick.py`

**왜**: 리뷰 감성 분석은 문장마다 감성/주제 키워드 **수백 개**의 등장을 검사한다.
`for kw in keywords: if kw in sentence` 는 O(패턴 수 × 문장 길이) — 사전이 커질수록 느려진다.

**어떻게**: 전체 패턴으로 **트라이**를 만들고, KMP 실패 함수를 트라이로 일반화한
**실패 링크**를 BFS 로 연결한다. 텍스트를 **한 번만 스캔**하면서 모든 패턴의 모든
등장 위치를 찾는다.

- 구축 O(패턴 길이 합), 검색 **O(텍스트 길이 + 매칭 수)** — 패턴 수와 무관
- 실패 링크의 output 병합으로 "가성비" 안의 "성비" 같은 접미사 패턴도 함께 보고
- 자동자는 불변이므로 서비스 생성 시 1회 구축 후 모든 요청이 재사용

**도메인 특화 처리** (실제 리팩터링 중 발견한 함정들):

1. **반대 극성 스팬 억제**: "안 좋아요"는 부정 "안 좋"과 긍정 "좋"이 동시에 매칭된다.
   더 긴 반대 극성 매칭에 완전히 포함된 매칭을 무효화해 오분류를 막는다.
2. **단음절 키워드 배제**: "품"은 "제품/품질"에, "울"은 "겨울"에 걸린다.
   부분 문자열 매칭의 정밀도 함정이라 사전에서 제외했다.
3. **한국어 불규칙 활용**: ㅂ불규칙(아쉽→아쉬워), 르활용(느리→느려)은 어간
   표기가 변하므로 대표 활용형을 사전에 함께 등록했다.

**면접 포인트**: KMP 와의 관계(단일 패턴의 실패 함수를 다중 패턴 트라이로 확장),
BFS 가 보장하는 위상 순서(부모의 실패 링크가 자식보다 먼저 확정), 실무 사용례
(침입 탐지 스노트, 욕설 필터, grep -F 의 다중 패턴).

### 3.6 Okapi BM25 랭킹 — `analysis/bm25.py`

**왜**: 기존 코드는 "키워드가 보이면 +N점" 가산 방식이었다. 이 방식은
(1) 모든 문서에 나오는 흔한 단어("무신사", "제품")와 희귀한 단어를 같은 가중치로 취급하고,
(2) 같은 단어의 반복 등장에 점수가 선형으로 부풀며,
(3) 문서 길이에 따른 우연 매칭을 보정하지 못한다.

**어떻게**: 정보 검색의 표준 랭킹 함수 BM25 로 교체.

```
score(D,Q) = Σ IDF(qᵢ) · (f(qᵢ,D) · (k₁+1)) / (f(qᵢ,D) + k₁ · (1 − b + b·|D|/avgdl))
```

- **IDF**: 흔한 단어의 변별력을 자동으로 죽인다 (수작업 가중치 튜닝 불필요)
- **TF 포화**: k₁로 반복 등장의 기여를 점근적으로 수렴시킴
- **길이 정규화**: b 로 긴 문서의 우연 매칭 페널티
- IDF 는 Lucene/ATIRE 변형 `ln(1 + (N−df+0.5)/(df+0.5))` 사용 — 원조 RSJ IDF 는
  df > N/2 인 단어에서 **음수**가 되어 "단어가 있으면 감점"되는 이상 동작이 있다
- 상위 k 추출은 전체 정렬 O(n log n) 대신 힙으로 **O(n log k)**

최종 점수 = BM25 정규화 점수(60%) + 도메인 규칙 가산(무신사 +20, 예산 적합 +15, 브랜드 +5).
통계적 관련도가 주가 되고, 검색으로는 알 수 없는 비즈니스 우선순위만 규칙으로 보탠다.

**면접 포인트**: TF-IDF 와의 차이(포화·길이 정규화), 파라미터 의미(k₁=1.5, b=0.75 가
사실상 표준), Elasticsearch/Lucene 의 기본 스코어러가 BM25 인 이유.

### 3.7 한국어 토크나이저 (음절 bigram) — `analysis/tokenizer.py`

**왜**: BM25 는 토큰 단위로 동작하는데, 한국어는 조사·어미가 붙어 어절 단위 매칭이
잘 깨진다 ("미니멀" ↔ "미니멀리즘"). 형태소 분석기(KoNLPy)는 JVM 의존성이 무겁다.

**어떻게**: 한글 연속 구간을 통짜 토큰 + **음절 bigram** 으로 색인한다.
"미니멀리즘" → `[미니멀리즘, 미니, 니멀, 멀리, 리즘]`. 쿼리 "미니멀"의 bigram
(미니, 니멀)이 겹쳐 부분 일치가 성립한다.

**트레이드오프**: 형태소 경계와 무관한 bigram(재현율↑ 정밀도↓)이 생기지만,
흔한 bigram 은 IDF 가 낮아 BM25 가 자동으로 가중치를 죽인다 — 두 컴포넌트가
서로의 약점을 보완하는 조합.

### 3.8 Levenshtein 편집 거리 — `analysis/similarity.py`

**왜**: 여러 검색어로 수집한 후보에는 같은 상품이 표기만 다르게 반복된다
("나이키 에어포스 1 '07" vs "나이키 에어포스1 07"). URL 비교로는 못 잡는다.

**어떻게**: 삽입/삭제/치환 DP. 두 가지 최적화:

- **2행 롤링**: 전체 m×n 테이블 대신 직전 행만 유지 → 공간 O(min(m,n))
- **임계값 조기 종료**: 중복 판정은 "거리 ≤ k" 여부만 필요하다.
  DP 행 최솟값이 k 를 넘으면 이후 행은 단조 비감소이므로 즉시 중단.
  또한 |len(a)−len(b)| > k 면 DP 없이 거절 (길이 차는 거리의 하한).

**면접 포인트**: DP 점화식 유도, 행 최솟값 단조성 증명, 실무 대안
(대량 데이터라면 MinHash/SimHash 같은 LSH 계열로 후보쌍을 줄인 뒤 정밀 검사).

### 3.9 스레드풀 병렬 검색 — `infra/search_client.py`

**왜**: 에이전트 하나가 검색어 4~8개를 던진다. 순차 호출이면 지연이 쿼리 수에 비례.

**어떻게**: `ThreadPoolExecutor` 로 fan-out. 네트워크 I/O 대기 중에는 GIL 이
해제되므로 **I/O 바운드 작업은 스레드로 실효 병렬화**된다. 지연 ≈ 가장 느린 쿼리 1개.

**면접 포인트**: GIL 이 있는데 왜 스레드가 유효한가(블로킹 I/O 중 GIL 해제),
CPU 바운드라면?(multiprocessing), asyncio 로 안 한 이유(§4.3).

## 4. 설계 결정 기록 (ADR)

### 4.1 프로토콜 기반 DI — 프레임워크 없이

`SearchClient`, `ReasonGenerator` 를 `typing.Protocol` 로 정의하고 생성자 주입.
DI 프레임워크 없이도 구조적 타이핑으로 결합을 끊었다. 결과: 테스트 139개가
네트워크·API 키 없이 0.2초에 완주.

### 4.2 도메인 모델과 API 스키마 분리

`domain/models.py`(dataclass) 와 `api/schemas.py`(pydantic) 를 분리.
직렬화 형식(API 계약)과 내부 표현을 독립적으로 진화시킬 수 있고,
서비스/분석 계층이 웹 프레임워크에 오염되지 않는다.

### 4.3 FastAPI 핸들러를 sync(def) 로

Tavily SDK 가 블로킹이므로 `async def` 로 감싸면 이벤트 루프가 멈춘다.
`def` 핸들러는 FastAPI 가 스레드풀에서 돌려주므로 루프 블로킹이 없다.
async HTTP 클라이언트로의 전환은 인터페이스 뒤에 격리되어 있어 점진 도입 가능.

### 4.4 LLM 은 선택적 + 자동 폴백 (graceful degradation)

추천 이유 생성은 `OpenAIReasonGenerator`(있으면) → 실패 시
`HeuristicReasonGenerator` 로 자동 폴백. **LLM 장애가 추천 기능 전체를 죽이지 않는다.**
핵심 랭킹은 LLM 없이 BM25 로 동작하므로 비용·지연·장애 리스크가 코어 경로에 없다.

### 4.5 검색 쿼리 수 축소 (리뷰 16개 → 6개)

기존 코드는 유사 쿼리를 16개까지 던졌다. 검색 API 는 과금 자원이므로
서로 다른 정보를 주는 쿼리만 남기고, 커버리지는 병렬화 + 캐시로 보전했다.
